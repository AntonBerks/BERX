# BERX FUTURE CORE — Архитектурная карта

Статус: аудит выполнен по реальному коду. Ничего существующего не переписано.
RUNTIME: не проверялось (нет PHP/MySQL в среде).

---

## Аудит семи ядер

### 1. SOCIAL GRAPH — ЧАСТИЧНО, фрагментирован
Реально существуют, но как **четыре несвязанных механизма**:
- OSSN friends (`ossn_relationships`)
- `OssnCircles` → `ossn_circle_members` (приватные круги + видимость постов)
- `OssnBusiness` → `ossn_business_team` (роли owner/manager/staff)
- `OssnGroup` (участники сообществ)

Плюс рёбра-отношения: `berx:place:saved`, `berx:event:going`.

**Пробел:** нет единого запроса «все связи пользователя X». Каждый домен спрашивает свою таблицу. Для Feed ranking и Discovery это блокер.

### 2. WORLD GRAPH — ЕСТЬ, узкий
`OssnGeo` (haversine, `object_type` = place|event), `OssnPlaceHours` (структурированные интервалы), Nearby + Moments + Impressions.

**Пробел:** `OssnTrips`/`OssnExperiences` связывают места и события, но **не участвуют в гео-слое** — маршрут поездки не является пространственным объектом.

### 3. FEED / DISCOVERY — ✅ РЕАЛИЗОВАНО (ядро №2)
Было: `feed.php` вызывал `GetUserPosts()` — только собственная стена, ноль ranking-сигналов. Хуже того: при аудите вскрылся реальный, ранее незамеченный баг — `searchObject()` валидирует `offset` как 1-based номер страницы, а клиент всегда шлёт буквальный `0` (`api.feed(limit, 0)`), из-за чего запрос молча проваливал валидацию и **лента была пустой всегда, для всех пользователей**. Это был не "примитивный ranking", а полностью неработающая лента.

**Исправлено:** `feed.php` теперь берёт реальный, уже существовавший, но никогда не вызывавшийся `OssnWall::getFriendsPosts()` (друзья + сам + админы, реальная видимость PUBLIC/FRIENDS) через `page_limit=>false` — тот же рабочий паттерн, что уже использовал `friends.php`, — получает плоский пул кандидатов и сам пагинирует его через `array_slice()` с 0-based offset, как и ожидает клиент. Ранжирование — прозрачная gravity-функция `(engagementScore+1)/(age_hours+2)^1.6` поверх уже реальных сигналов `OssnSignals` (like/comment/share/save), без AI.

### 4. MATCH — ПОЛНЫЙ
`OssnDating`: профиль, discover, recommendedProfiles, interests/pass/undo, mutual matching, unmatch, приватные фото с контролем доступа, privacy-флаги. Обёрнут полностью (Wave 5).

### 5. EXPERIENCE — ЕСТЬ, цепочка разорвана
`OssnExperiences` (якорь место/событие + участники), `OssnTrips` (дни/остановки), отзывы, points.

**Пробел:** нет **check-in**. Цепочка `DISCOVER → GO → EXPERIENCE → VERIFY → REVIEW → EARN` рвётся на VERIFY: невозможно подтвердить, что человек реально был на месте. Из-за этого «Verified Experience» построить нельзя честно.

### 6. IDENTITY / TRUST — МИНИМАЛЬНЫЙ
Есть: `verified` на местах (только админ), claims на владение бизнесом (ручное одобрение), роли в командах.

**Пробел:** нет уровня доверия пользователя. Отзыв новичка и отзыв человека с 200 реальными действиями неразличимы.

### 7. EVENT LAYER — ОТСУТСТВУЕТ ⚠️
Единственное, что есть — `OssnNearbyImpressions` (4 типа, только для мест).

**Пробел, самый важный:** каждая подсистема пишет свои следы отдельно (points, notifications, impressions, streak). Нет единого доменного лога. Без него **невозможны** Feed ranking, Trust scoring, Analytics и Verified Experience.

## Open-source: проверено, и вывод — не нужен

**Честное ограничение среды:** npm/composer/apt в этой песочнице отдают 403. Любая внешняя зависимость сейчас не может быть ни установлена, ни проверена на реальную работу. Поэтому рекомендовать пакет «на веру» я не буду.

**Но по существу зависимость и не требуется:**

| Ядро | Кандидаты | Решение |
|---|---|---|
| Event Layer | Kafka, RabbitMQ, EventStore | **Отклонено.** Внешний брокер для однопроцессного PHP/MySQL — несоразмерная инфраструктура. Реальное решение: одна индексированная таблица + тонкий класс. |
| Feed ranking | Elasticsearch, Recombee, OpenSearch | **Отклонено.** Ранжирование по реальным сигналам (свежесть, расстояние, граф, engagement) — это SQL + весовая функция, а не поисковый кластер. ES оправдан на порядки большем объёме. |
| Graph | Neo4j, ArangoDB | **Отклонено.** Второй источник истины прямо запрещён каноном. Граф уже в MySQL. |
| Trust | — | Чистая доменная логика поверх Event Layer. |
| Geo | PostGIS | **Отклонено.** Требует смены СУБД. Haversine в `OssnGeo` уже работает. |

**Вывод: все семь ядер закрываются собственным кодом поверх существующих MySQL/OSSN. Новых зависимостей — ноль.** Это не компромисс из-за песочницы, а правильное решение для этого масштаба.

## Порядок реализации (по рычагу)

1. **EVENT LAYER** ← фундамент, разблокирует 3, 6, 7. *Реализуется первым.*
2. **FEED RANKING** — читает Event Layer + существующие сигналы.
3. **TRUST** — агрегирует Event Layer.
4. **CHECK-IN** — замыкает Experience-цепочку, даёт Verified Review.
5. **UNIFIED GRAPH** — единое чтение связей.
6. **WORLD GRAPH+** — Trips/Experiences в гео-слой.

---

## Правила Future Core

- Event Layer **только дописывает** (append-only). Никаких UPDATE/DELETE, кроме ретенции.
- Все счётчики — живой `COUNT()` по реальным строкам. Никаких кэшированных агрегатов, которые могут разойтись с правдой.
- Ranking — **прозрачная весовая функция**, а не «магия». Никакого AI (канон).
- Trust считается **только** из реальных подтверждённых действий. Ни одного выдуманного очка.
- Ни один существующий модуль не ломается: всё — надстройка.
