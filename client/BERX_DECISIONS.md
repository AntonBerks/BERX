# BERX — Decision Log

Read this before changing an established decision. Only overturn one with new evidence, not preference.

## Stack
- **Backend stays OSSN/PHP/MySQL.** Evaluated a 456-screen microservices brief (Postgres/Mongo/Redis/Kafka, Swift/Kotlin/Next.js) and explicitly declined it — the existing OSSN core is mature, working, and the redesign is layered on top of it, not a replacement.
- **Mobile stays React Native + TypeScript**, consuming `/api/v1/*`. No native Swift/Kotlin.
- **API surface is `/api/v1/` only.** No undocumented endpoints. New resources (Places, Events, Comments, Sessions, Community requests) were added as new files under `components/OssnApi/v1/`, never by modifying the dispatcher's routing convention.

## Design
- **Accent color: warm gold `#D9A93F`, everywhere except the one scoped exception below. CYAN `#4fd6e8` IS RETIRED.** Full history, in order: orange `#ff6a00` (rejected, "я устал видеть этот оранжевый"); cyan `#4fd6e8` (locked for a long stretch, "do not reopen without an explicit, unambiguous instruction"); violet `#8b5cf6` proposed once, not adopted as a systemic accent (kept alive only as one endpoint of the scoped gradient exception below). Then an explicit, unambiguous "BERX WORLD — FULL TRANSFORMATION MASTER DIRECTIVE" instruction retired cyan outright ("ZERO TURQUOISE... Do NOT use #4FD6E8... Do NOT automatically replace it with another single 'brand color'... Create a completely new BERX visual identity") — the exact bar this log's own prior entry set for reopening the decision. Replacement: warm gold `#D9A93F` (`accentHover` `#EABD5C`, `accentSoft` `rgba(217,169,63,0.16)`), a hue family deliberately distinct from every color this project has already tried and rejected (not a disguised return to the rejected orange — hue ≈45° gold/brass vs. the rejected ≈24° red-orange — and not a return to violet or cyan either). Chosen and applied autonomously per that directive's explicit "do not ask about obvious implementation decisions" instruction; the specific hue is the one part of this that's genuinely a judgment call, not a locked business decision — if it's wrong, it is a one-file mobile change (`packages/design-system/src/tokens/index.ts`) plus one CSS-variable definition (`themes/berx/plugins/default/css/core/default.php`'s `--berx-accent`), by design, specifically so this is cheap to iterate on unlike the earlier repaints. Applied systemically: both the mobile token file and every real usage across the live PHP web theme (`--berx-accent`/`--berx-accent-hover`/`--berx-accent-soft` and their ~15 inline fallback literals across 12 theme/component CSS files) — not just one side of the stack.
- **Day environment tokens exist (`colorsDay` in the same tokens file) but are not yet wired to a runtime switch.** Defining the palette and actually re-theming ~80 screens (all of which compute a static, Night-only `StyleSheet` once at module load) are different-sized jobs; shipping the values without the switch, rather than not shipping them, keeps this decision documented and gives the next pass a real starting point instead of a blank one.
- **Editorial CTA gradient — violet `#8b5cf6` → orange `#ff6a00` — scoped exception, unaffected by the cyan retirement above**, added with an explicit reference image and confirmed in-session. Used ONLY for the one social "Follow"-class CTA component, `BerxGradientCTA` (design-system) — never spread to any other button, badge, or accent use. Reuses two hex values already on this project's own reject list *as a systemic accent* — that's exactly why they were safe to reuse in a deliberately narrow, non-systemic role instead of inventing new ones. If a future change wants this gradient anywhere else, that's a new instruction, not an extension of this one.
- **Premium Dark, glass-on-floating-elements-only**, not glass on entire pages. Media is the primary visual element; chrome supports it.

## Engineering rules (non-negotiable, repeated project-wide)
- **No fake functionality.** No button whose action doesn't reach real persistence. Verified case-by-case: Places/Events booking-adjacent features (table reservations, ticket payments) do NOT exist — not built, not faked, documented as a real backend gap instead.
- **Ownership checks live at the query/method level**, not as a separate "trust me" check before the real one — e.g. `OssnApiToken::revokeSessionById($id, $userGuid)` puts both in the WHERE clause; a foreign id matches zero rows rather than someone else's data.
- **A client method is only added the same day its PHP endpoint ships**, never speculatively (see the header comment in `packages/api/src/client.ts`).
- **Every new capability was checked against the real class method inventory before being called** — several real bugs were caught this way before shipping (see `BERX_CHANGELOG.md`), including calling non-existent engine functions and misusing methods with wrong argument contracts.

## Known environment limitation
This chat environment has the mobile source tree (`/home/claude/berx/client`) but **no `package.json`, no `node_modules`, no native `ios/`/`android/` projects, no Metro config**. `tsc` (v6.0.3) is available globally and gives a real, valid typecheck signal for the TypeScript source. Full RN build/run/test (`npx react-native run-ios`, Jest, ESLint with the project's real config) cannot be executed here — those checks are real work items for wherever the full toolchain lives, not skipped by choice.
