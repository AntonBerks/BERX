# BERX API v1 — Pagination Strategy

Честная фиксация текущего состояния — не добавлял искусственный
limit/offset туда, где реальный метод класса его не поддерживает
нативно.

| Список | Статус | Механизм |
|---|---|---|
| `GET /feed` | **paginated** | `limit`/`offset` query-параметры → `OssnWall::GetUserPosts($user, ['limit'=>.., 'offset'=>..])`, подтверждено реальным ключом в `searchObject()`'s default array |
| `GET /dating/discover` | **paginated** | `limit`/`offset` → `OssnDating::recommendedProfiles()`, параметры уже существовали в методе, построенном ранее в этой сессии |
| `GET /search/users` | **naturally bounded** | `OssnUser::searchUsers()` не принимает limit/offset в том виде, в каком я его вызываю (передаю только `wheres`) — реального лимита нет вообще. Практически ограничено тем, что запрос по имени обычно возвращает немного строк, но это не защита, а везение. **Требует доработки backend-метода**, если список пользователей на сайте вырастет. |
| `GET /dating/matches` | **naturally bounded** | `listMatches()` возвращает ВСЕ совпадения без лимита. Для реального продукта с тысячами пользователей это станет проблемой, но при текущем масштабе сайта (единицы пользователей) — не критично сейчас. |
| `GET /conversations` | **naturally bounded** | `recentChat()` физически поддерживает `$count` параметр (макс. режим), но не `limit`/`offset` в удобном для API виде — возвращает по одному последнему сообщению на диалог, так что рост ограничен количеством диалогов, а не сообщений. |
| `GET /conversations/{id}` | **requires future backend extension** | `getWith()` использует `input('offset_message_xhr_with')` — жёстко захардкоженное имя input-параметра, завязанное на веб-форму, а не на чистый API-параметр. Не стал подключать это "как есть", чтобы не плодить скрытую зависимость от глобального `input()`-состояния; настоящая пагинация переписки требует правки метода класса. |
| `GET /notifications` | **paginated** | `limit`/`offset` → `OssnNotifications::searchNotifications()`, использует реальный встроенный механизм пагинации ядра (`page_limit`, `offset`) |
| `GET /stories` | **naturally bounded** | `listActiveForViewer($viewerGuid, $limit=40)` — жёсткий верхний предел 40 сгруппированных авторов, захардкожен на уровне метода (не параметризован через API сейчас) |
| `GET /stories/own` | **naturally bounded** | `listOwnActive()` не имеет лимита вообще, но естественно ограничено 24-часовым временем жизни историй — у одного пользователя редко бывает много активных Stories одновременно |

## Итог

Два эндпоинта (`feed`, `dating/discover`) и один (`notifications`) —
честная, реальная пагинация. Остальные — либо естественно ограничены
характером данных, либо требуют доработки на уровне PHP-класса, а не
просто добавления query-параметров в API-обёртку — не стал
симулировать пагинацию, которой на самом деле нет.
